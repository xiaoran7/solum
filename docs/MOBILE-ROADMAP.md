# Solum 移动端产品与技术路线总览

> 更新日期：2026-08-22  
> 本文是快速理解“接下来做什么”的摘要，不取代权威文档：设计冲突以 [ARCHITECTURE.md](ARCHITECTURE.md) 为准，当前行为与隐私承诺以 [PRIVACY.md](PRIVACY.md) 为准，实际执行项和状态以 [TODO.md](TODO.md) 为准，历史取舍见 [MISC.md](MISC.md)。

## 1. 一句话定位

Solum 是一个 Mobile-only、Android-first 的本地优先个人 Agent：从手机上的真实信息源理解用户，把有价值的信息转成可追溯的记忆、日程与提醒，并通过唯一 Solum Server 提供云端 AI 和端到端加密备份。

产品最终覆盖 Android、iOS、HarmonyOS；当前只主开发和验收 Android，项目成熟后补齐 iOS 与鸿蒙。桌面端和网页端退出产品范围。

## 2. 已拍板的核心决定

1. **移动端三平台，Android 优先。** 三端可以使用不同平台壳层，但必须共享领域语义、服务端 API、隐私边界和备份格式。
2. **不做网页产品。** 服务端只提供 API，不提供注册、登录或用户控制台网页。
3. **不做桌面产品。** 不再发布 Windows/macOS/Linux 客户端；CLI 只作测试和迁移工具。
4. **一个服务端。** 账号、AI、备份、恢复信封和必要元数据全部使用同一个 `solum-cloud + PostgreSQL`、同一个 origin 和同一个账号身份。
5. **多设备双向同步退出目标架构。** 当前活跃手机是单一业务权威；换机通过端到端加密版本化备份恢复，不维护手机/电脑或多台手机长期并发写入。
6. **备份尽量完整。** 全部可移植用户数据原则上进入加密快照；平台权限、系统闹钟注册、硬件密钥句柄和本机路径只恢复配置意图，再由目标系统重新授权或绑定。
7. **先保护数据，再删除旧链路。** 当前桌面、push/pull、oplog 和旧 relay 都是迁移态；备份/恢复闭环验收并生成可恢复快照前，不能先删掉现有远端历史。

## 3. 产品价值主链

后续所有功能都应服务于这条主链：

```text
信息进入手机
    ↓
来源标记、权限判断、去重与关联
    ↓
形成候选事实 / 日程 / 提醒 / 待确认动作
    ↓
用户确认或规则安全执行
    ↓
进入可追溯记忆与 Agent 上下文
    ↓
在正确时间提供提醒、建议或复盘
    ↓
完整数据端到端加密备份
```

近期不再以“功能数量”衡量进展，而以四项结果衡量：看见的信息是否重要、理解是否准确、提醒是否可靠、数据是否可恢复。

## 4. 目标架构

```text
Android（当前） / iOS、HarmonyOS（成熟后）
├── 本地领域数据存储（业务权威）
├── 信息源与平台权限适配
├── Agent Orchestrator
├── 本地提醒与后台任务
├── 记忆、来源追溯与用户纠错
└── 规范化快照 → 压缩 → AEAD 加密
                         │
                         ▼
                 唯一 Solum Server
                 ├── 账号与会话
                 ├── AI 网关与额度
                 ├── 加密备份版本
                 ├── 备份密钥恢复信封
                 └── 必要的非正文元数据
```

服务器可以验证用户和保存密文，但不能解密备份正文。AI 请求是另一条边界：服务器和上游模型会在本次调用期间处理用户明确发送的最小上下文，但不因此获得备份解密权。

## 5. 端到端加密备份与换机恢复

### 5.1 格式原则

- 使用规范化逻辑数据，不直接上传 Android SQLite、iOS Core Data 或 HarmonyOS relationalStore 文件。
- 格式带独立 `protocol_version` / `schema_version`，字段使用稳定 ID 和明确语义。
- 覆盖日程、提醒、记忆、人格、行为、通知处理结果、健康、组件、完整对话、资料、Agent 设置和提供商允许迁移的账户配置/凭据。
- 压缩后使用 AEAD 加密；AAD 绑定用户 UUID、设备代次、备份版本、创建时间和格式版本。
- Android、iOS、HarmonyOS 使用同一组规范化备份夹具做交叉导入测试。

### 5.2 恢复安全

- 新手机先下载并校验密文、认证标签、哈希、容量和版本兼容性。
- 导入临时数据存储并完成完整性检查后，才原子切换为正式数据。
- 本机已有数据时必须预览并明确选择，不允许静默覆盖。
- 账号维护单调递增的 active generation；新手机确认接管后，旧手机不能继续上传成为“最新备份”。
- 备份保留多个完整版本；失败或半包不得覆盖最近一个可恢复版本。
- 除密码包装外，设计用户自行保存的恢复码；密码和恢复码都丢失时，服务器不能解密或找回数据。

### 5.3 平台绑定能力

以下内容不是跨平台数据，恢复后需要重新授权或绑定：

- 通知读取与推送权限
- 健康平台权限与来源映射
- 系统闹钟/后台任务当前注册状态
- 电池、自启动和后台运行策略
- Secure Enclave / Keystore 等硬件密钥句柄
- 本机文件路径
- 已过期或被撤销的 OAuth 会话

备份可以保存“用户以前启用了什么”的意图，但不能把配置字节恢复成功冒充平台能力已恢复。

## 6. 信息源优化

### 6.1 信息源中心

应用提供统一信息源页，每个来源显示：

- 当前平台是否支持
- 是否已授权、最近一次成功采集和错误状态
- 是否允许形成记忆
- 是否允许发给 AI
- 是否进入加密备份
- 数据保留期和删除入口

平台能力不得伪装一致。Android、iOS、HarmonyOS 通过能力矩阵声明通知、健康、日历、分享、后台、闹钟和安全存储支持度，UI 如实呈现差异。

### 6.2 统一候选信息

信息源保留自己的原始数据边界，再向 Agent 管线产出统一候选信息：

```text
source_id / external_id
occurred_at / captured_at
原始证据引用
敏感级别
可信度
有效期
是否允许 AI / 记忆 / 备份
候选动作
```

原始证据、派生事实和执行动作必须分层，AI 推测不能伪装成来源直接提供的事实。

### 6.3 来源优先级

优先建设：

1. 现有通知采集的稳定性、降噪和关联。
2. 系统“分享给 Solum”入口，接收用户主动选择的文字、网页、图片和文件。
3. 系统日历只读接入，再做经过确认的写入。
4. Health Connect / 各平台健康能力的本地趋势摘要。
5. 邮件中的高价值事件提取，不继续扩张为完整邮件客户端。
6. 位置、出行等高敏感来源在核心成熟后再评估。

同一事件可能同时来自日历、邮件、通知和用户输入，必须做稳定 ID、内容指纹、时间邻近和实体匹配，尽量合并补全而不是重复建提醒。默认可信度顺序为：用户明确确认 > 权威结构化来源 > 原始邮件/订单 > 通知 > AI 推测。

## 7. Agent 与记忆质量

每条长期记忆应具备：来源、形成时间、可信度、最后验证时间、有效期和删除/纠错入口。

必须区分：

- 用户确认事实
- 来源直接提供的信息
- Agent 推测
- Agent 建议
- 待确认动作

用户说“不是这个意思”“已经过期”“以后别这样处理”时，不只修改当前记录，还应形成待确认的来源规则或偏好修正。验证码、快递状态、临时行程等短生命周期信息不能永久污染长期记忆；人格偏好和长期习惯可以保留但仍需来源与版本。

健康数据优先在本地转为睡眠、步数、心率相对个人基线的趋势摘要；原始采样可以加密备份，但不应成为日常 AI 上下文的大体量噪声。

## 8. 移动端信息架构与排版

保持四个稳定根入口，不新增第五个底栏 tab：

```text
今天 / 记忆 / 计划 / 搜索
```

“今天”是主工作面，从上到下只放：

1. **现在**：当前场景与正在发生的事。
2. **需要确认**：候选日程、记忆、过滤规则和高风险动作。
3. **接下来**：近期日程与提醒。
4. **今日观察**：健康、习惯和信息摘要。
5. **快速输入**：文字、语音、分享内容。

信息源中心进入“账号/设置 → 信息源”，不扩张底栏。备份正常时只显示“已安全备份 · 时间”；只有连续失败、空间不足或备份校验异常时才提升为需要处理的状态。用户界面不展示 push、pull、blob、seq、relay 等实现词。

移动端优先使用扫读列表、底部抽屉、分段控件和一屏一个主要动作；减少桌面表格、横向滚动和多列操作。平板/折叠屏可以增加会话栏或今日面板，但不能建立第二套桌面式信息架构。

## 9. 暂停扩张的能力

以下能力可以保留已有实现，但在主链成熟前不继续扩展：

- 桌面端和桌面专属行为
- 多设备实时同步
- 电脑福利监控与桌面告警
- BloomXP 双向互通
- 自定义组件的新视图、复杂 schema 与动态导航
- GenUI 新组件类型
- 完整邮件客户端方向
- 新的高敏感信息源
- iOS/HarmonyOS 的立即开发

暂停不是立刻删除。凡涉及现有用户数据或迁移路径，必须等替代方案验收后再退役。

## 10. 实施阶段

### 阶段 0：保护迁移边界

- 冻结桌面和旧同步的新功能。
- 删除网页 Dashboard 前确认客户端不依赖它。
- 盘点生产账号、legacy 租户、远端 blob 和本地 profile。
- 保持当前数据可读、可备份，不做破坏式清理。

### 阶段 1：Android 备份与恢复地基

- 定义跨平台备份 schema、夹具、加密信封和恢复码。
- 实现唯一服务端 `/v1/backups/*`。
- 完成 Android 完整备份、坏包防护、版本列表、设备接管和原子恢复。
- 为现有数据生成可验证快照后，再退役 push/pull、oplog 和旧 relay。

### 阶段 2：信息源基础

- 信息源注册表和平台能力矩阵。
- 统一候选信息、来源追溯、权限分层、去重与关联。
- 完成分享入口和系统日历。
- 优化通知与健康摘要。

### 阶段 3：Agent 质量闭环

- 事实/推测/建议分层。
- 记忆可信度、有效期与验证时间。
- 用户纠错反哺来源规则。
- 本地可审计的 Agent 上下文和信息源质量报告。

### 阶段 4：Android 日常成熟

- 持续 dogfooding，收敛后台、耗电、提醒、权限与恢复体验。
- 完成数据无损、备份可恢复和提醒可靠性门槛。
- 冻结跨平台领域与备份协议的首个稳定版本。

### 阶段 5：iOS 与 HarmonyOS

- 先通过同一服务端契约和备份夹具，再接本地存储。
- 再实现各平台通知、健康、后台、闹钟和安全存储适配。
- 保持相同用户心智，不伪装平台能力完全一致。

## 11. 开始其他平台前的成熟门槛

- Android 连续真实使用至少一个月。
- 多次完整备份、换机恢复和旧版本迁移无数据丢失。
- 坏包、断网、半包和服务端回滚演练不会破坏最后可用版本。
- 提醒到达稳定，后台与电池行为可接受。
- 通知误判、重复事件和错误记忆有可用纠错入口。
- 信息源权限、AI 上行和备份边界对用户足够清楚。
- 跨平台备份 schema 与测试夹具进入稳定版本。

## 12. 当前最优先的五件事

1. 冻结桌面、旧同步和非核心连接器扩张。
2. 定义平台无关的备份 schema、恢复码与 active generation。
3. 实现 Android → Server → Android 的完整备份恢复闭环。
4. 建立信息源注册表、候选信息格式和来源追溯。
5. 完成 Android 分享入口与系统日历，再优化通知去重和健康摘要。
