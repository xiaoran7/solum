# 踩坑集

> 强制记录：任何调试超过几分钟、走过弯路、被坑过的问题都要写在这里，不管最后是否解决。格式：现象 / 根因 / 解决方式 / 如何避免。

## 2026-08-13 后台监控不要用“每次启动都开 URL”管理控制台标签

- **现象**：独立福利监控每次双击都会 `Start-Process http://127.0.0.1:17321/`，福利恢复时也主动打开详情页；长期运行会积累浏览器标签和内存占用。
- **根因**：后台检测、控制台展示和事件详情被混成同一个生命周期。普通 Windows 进程没有可靠、浏览器无关且不侵入用户会话的“按 URL 查找并聚焦现有标签”接口。
- **解决**：监控服务保持单实例；控制台标签用随机 client id 向回环 API 发送心跳和关闭上报，重复启动只在服务存在且没有活跃页面租约时打开控制台。恢复事件只通知并携带详情 URL，不主动打开页面。
- **避免**：后台服务与 UI 页面必须可独立存活；不要用反复打开 URL 代替实例发现或窗口管理，也不要扫描浏览器进程、调试端口或用户配置来猜标签状态。

## 2026-08-13 Android Release 输出被占用时不要强杀未知进程

- **现象**：`:app:packageArm64Release` 编译、压缩和签名前步骤都完成，但 Gradle 无法删除旧 `app-arm64-release.apk`，最终打包失败。
- **根因**：旧 APK 被资源管理器、杀毒软件或其他未知进程持有；Gradle 会先清理固定输出目录，因此并非代码或签名错误。
- **解决**：让 `app/build.gradle.kts` 的 buildDir 接受 `solumBuildDir` Gradle 属性覆盖，在独立目录构建新版本；构建产物目录用 `app/build-*/` 忽略。旧 APK 原样保留作为回滚产物。
- **避免**：不要为释放构建产物而强杀未知进程；版本化或临时 buildDir 比破坏式清理更可审计。

## 2026-08-12 relay 仪表盘直接登录账号服务必须显式处理 CORS

- **现象**：relay 的静态仪表盘和 `solum-cloud` 通常是两个域名；页面直接调用 `/v1/auth/login` 时，curl/原生客户端正常，浏览器却会在预检阶段拦截。
- **根因**：账号服务原来只面向原生客户端，没有 CORS 响应。把账号 URL 做成用户可填再由 relay 服务端代请求会扩大为 SSRF；开放 `*` 又会让任意网站借浏览器发起登录。
- **解决**：`solum-cloud` 增加 `SOLUM_ALLOWED_ORIGINS` 精确来源白名单和 OPTIONS 支持，只对命中的 origin 回显许可；仪表盘密码不保存，短期会话只留页面内存。主仓与 Harmony 的同源服务端同时更新。
- **避免**：任何“服务 A 托管页面，页面登录服务 B”的设计，在写 UI 前先画清浏览器 origin。原生 HTTP 能通不代表浏览器能通；优先精确 CORS 白名单，不用通配符，也不把用户可控目标转成后端代理。

## 2026-08-12 PowerShell HttpListener 不应推断 JSON 请求体编码

- **现象**：Benefit Monitor 的英文/空配置保存正常，一旦默认渠道名含中文，`ConvertFrom-Json` 报“应为 : 或 }”，浏览器看到 400。
- **根因**：前端只发 `application/json`，`HttpListenerRequest.ContentEncoding` 在 Windows PowerShell 5.1 下没有稳定落到 UTF-8；请求体中的中文先被错误解码，随后才交给 JSON 解析器，字符串引号边界因此损坏。
- **解决**：前端声明 `application/json; charset=utf-8`，服务端 `StreamReader` 同时固定使用无 BOM UTF-8 并允许 BOM 检测。真实浏览器重新保存三条中文预设并成功发出账号租户测试告警。
- **避免**：本地 HTTP API 也要把线上的编码契约写完整；不要因为页面和服务在同一台 Windows 机器上就信任平台默认编码。

## 2026-08-12 Kotlin daemon 跨 C/D 盘增量编译失败不等于 Gradle 构建失败

- **现象**：Android Kotlin 编译先打印 `this and base files have different roots`，一边是 `C:\Users\...\.cargo\registry` 的 Tauri Kotlin 源码，一边是 `D:\ClaudeSpace\...\gen\android`，随后出现 `Daemon compilation failed`。
- **根因**：Kotlin 增量缓存尝试把 C 盘和 D 盘文件都转成相对路径，Windows 不存在跨盘相对路径；这是 daemon/增量编译器的路径假设，不是业务 Kotlin 语法错误。
- **解决**：继续读取完整 Gradle 结果。当前插件会自动显示 `Using fallback strategy: Compile without Kotlin daemon`，非 daemon 编译随后完成，最终以末尾 `BUILD SUCCESSFUL` 为准。本次明确运行 `.\gradlew.bat :app:compileArmDebugKotlin --console=plain`，新告警服务成功编译。
- **避免**：不要在看到 daemon 堆栈第一屏时提前终止或误报代码失败；需要减少噪声时可停 daemon 后以非增量模式重跑。验证结论必须同时写明前置回退和最终构建状态。

## 2026-08-11 预构建 arm64 库必须配 `assembleArm64*`，跳错 Gradle 任务会产出无原生库 APK

- **现象**：`cargo tauri android build --debug --target aarch64` 已成功产出 `target/aarch64-linux-android/debug/libsolum_app_lib.so`，随后仍因 Windows 未开开发者模式而在 symlink 步骤失败。手工复制后若跑 `assembleArmDebug -x rustBuildArmDebug`，Gradle 会成功产出 APK，但日志明确提示 `armeabi-v7a` 没有 `.so`；这个包不能运行 Solum。
- **根因**：Gradle flavor 名 `arm` 对应 `armeabi-v7a`，`aarch64` 对应的是 `arm64`。`-x rustBuild...` 还会完全绕开仓库已经提供的 `SOLUM_PREBUILT_JNILIBS` 逃生门，让“任务成功”和“目标库进包”失去关联。
- **解决**：把已编译库复制到 `app/src/main/jniLibs/arm64-v8a/libsolum_app_lib.so`，设置 `SOLUM_PREBUILT_JNILIBS=1`，再运行 `gradlew :app:assembleArm64Debug`。最后不能只看 `BUILD SUCCESSFUL`：用 ZIP 条目确认 `lib/arm64-v8a/libsolum_app_lib.so` 存在，并用 `aapt dump badging` 核对 versionName/versionCode。
- **避免**：目标、flavor、ABI 必须成对：`aarch64 → arm64 → arm64-v8a`，`armv7 → arm → armeabi-v7a`。任何手工逃生构建都把“包内 native 条目 + badging”作为完成判据。

## 2026-07-29 切一页刷新全站、每次改动同步序列化，会把“数据正确”做成“界面迟钝”

- **现象**：每次切到任意视图都会并发刷新日程、提醒、记忆、邮箱、设置等全部域；启动时 `showView` 和 `initClock().then(refreshAll)` 还会重复一次。聊天历史每次变更立即同步 `JSON.stringify + localStorage.setItem`，理论上限远超 WebView 常见配额。
- **根因**：刷新函数只有“全部重取”一个粒度，缺少视图依赖表；把本地持久化误当成普通对象赋值，忽略 `localStorage` 序列化与写盘都阻塞主线程，也没有总预算与退出刷盘策略。
- **解决**：建立 `view → refreshers` 显式映射，切页只刷新目标域，启动只 hydrate 一次；幂等 IPC 以短 TTL 合并同轮重复请求，写入后 generation 失效。聊天历史延后 80ms 批量落盘、`pagehide` 强制刷盘，并按 2.4M 字符预算保留最近数据。
- **如何避免**：缓存前先写清“权威是谁、TTL 多久、哪类写入使它失效、哪些数据绝不能进缓存”；新增视图时必须把依赖登记到映射。任何 Web Storage 写入都按同步主线程 I/O 对待，既要节流，也要有生命周期末端的 flush 和配额退化路径。

## 2026-07-29 全屏隐私门不能把 Markdown 当纯文本，也不能等 IPC 完成后才给反馈

- **现象**：完整隐私政策直接露出 `**` 等标记；同意与拒绝按钮点击后，在写盘、退出或 IPC 异常期间没有即时变化，看起来像没有响应。
- **根因**：政策正文使用 `textContent` 整段写入，没有复用项目已有的安全 Markdown 渲染器；按钮的状态变化只依赖异步命令完成后的结果，而全屏门又会遮住普通 toast。Android 上关闭 WebView 窗口也不等同于结束应用任务。
- **解决**：摘要、全文和设置页统一走现有无依赖渲染器；按钮点击后立即切换文案并在门内显示进度，加入超时与可见错误；移动端拒绝命令明确结束进程。
- **如何避免**：全屏首启流程必须把“已收到点击、正在处理、处理失败”三种状态都放在自身层级；产品文案含 Markdown 时必须验证最终 DOM，不可只看源字符串；移动端退出不能用桌面窗口语义代替。

## 2026-07-27（晚）单行 `<input>` 会静默吃掉换行，多行采集正文的词边界就此消失

回移 capture 层时，「放入输入框」把待确认草稿的正文赋给对话输入框。

- **现象**：走查断言里 `chatInput.value` 是 `缴纳体检费明天 上午10点 到校医院合计 128 元`——预期的换行位置**直接消失**，`缴纳体检费` 和 `明天` 黏成一个词。
- **根因**：对话输入框是 `<input type="text">`，单行控件对赋进来的字符串会**静默剥掉换行符**（不是报错、不是转义，是直接丢）。多行采集正文（短信、订单、群通知都是多行）经它一过，词边界全没了，后续 `extract` 会把黏起来的字符串解错。
- **解决**：赋值前显式 `replace(/\s*[\r\n]+\s*/g, " ")` 把换行折成空格，而不是交给浏览器去丢。
- **如何避免**：**任何把多行文本塞进单行控件的地方都要先自己归一化。** 更一般的教训是这类缺陷 `cargo test` 和 JS 语法检查都测不到——它只在真实 DOM 里发生，是 AGENTS.md 坚持"交互改动必须过真实浏览器走查"的又一个实例。这次是走查断言直接把错误的字符串打出来才发现的；只看 diff 完全看不出问题（那行代码是再普通不过的 `input.value = draft.text`）。

## 2026-07-27（晚）clippy 的 `regex_creation_in_loops` 看不穿 `OnceLock` 宏，误报"循环里编译正则"

- **现象**：`capture.rs` 用本仓既有的 `lazy_re!` 宏（内部 `OnceLock::get_or_init`，只编译一次）在一个 `for` 循环里判断裸 URL，`cargo clippy -D warnings` 报 `error: compiling a regex in a loop`，质量门直接红。
- **根因**：lint 只看到宏展开后 `Regex::new(...)` 的调用点落在循环体内，**看不到外层 `OnceLock` 的记忆化**——是误报，实际每进程只编译一次。`extract.rs` 用同一个宏多年没触发，只因为它从没在循环体里调用过。
- **解决**：把 `lazy_re!(...)` 的结果**绑到循环外的局部变量**再在循环里用。语义完全不变，lint 满意，而且读起来更清楚。没有用 `#[allow]` 压掉——这里改写零成本，而 `allow` 会把同一个宏未来真正的误用一起放行。
- **如何避免**：本仓的 `lazy_re!` 在循环体里用之前先提到循环外。见到"明明记忆化了还报重复构造"这类 lint，先确认是不是 lint 看不穿宏，再决定是改代码还是加 allow；**能零成本改写就别 allow**。

## 2026-07-27 未显示的浏览器面板是零视口：fixed 元素坍缩、CSS transition 冻结，toast 可见性断言全是伪报

> **2026-07-27 晚复发一次，补两条可操作信息。** 走查隐私门时同一问题再现：`innerWidth/innerHeight` 都是 0，`#privacyGate`（`position:fixed; inset:0`）的 rect 坍缩成 40×52，`coversViewport` 算出 `false`；而 `getComputedStyle` 的 `display`、`overflow`、类名、调用序列全部正常——又是"一半量具好一半坏"的同一形状。
> ① **触发条件比原记录更具体**：用 `navigate` 把已有面板导到新 URL 时落到了一个没有布局的 tab（返回的 `tabId` 是 `seed`）；**重新 `preview_start` 拿到新 tab（`tab-2`）后视口立刻恢复 1280×720**，同样的断言全部转正。resize_window 无效。
> ② 所以恢复手法是**重开 preview 而不是反复 reload**。本次因为先按原记录的判据怀疑了量具、没有去"修"隐私门的 CSS，代价只有一次重开。



mock-IPC 走查「账号登录」UI 时用的是 Claude Code 应用内浏览器面板（用户未把面板切到前台）。

- **现象**：`#toast` 拿到了 `.show` 类、文案正确，但 `getComputedStyle` 的 `opacity` 在 80/400/900ms 三次采样中恒为 `0`，`getBoundingClientRect().width` 只有 34px（正好等于左右 padding 之和）——按 AGENTS.md 的渲染断言标准，结论会是「toast 完全没显示」。
- **根因**：面板未显示时页面不合成帧，`innerWidth`/`innerHeight` 都是 **0**。两个后果：① `position:fixed` 元素相对 0×0 视口布局，宽度坍缩、坐标为负；② CSS transition 不推进，`opacity` 冻结在起始值。类名、DOM 结构、`display` 这些**不依赖合成器的属性全部正常**——所以断言错得非常有迷惑性：一半量具是好的，一半是坏的。
- **判据（AGENTS.md「先怀疑量具」的又一实例）**：跑渲染断言前先查 `innerWidth > 0`；为 0 就只做结构化断言（computed `display`、`hidden`、textContent、类名、调用序列），把 opacity/rect/transition 类断言明确记为「未验证」，不要拿伪报去"修"一个正确的功能。本次 toast 逻辑经代码核对无改动且历史上验证过，按量具问题处理，不算产品缺陷。
- **对照**：普通文档流元素（表单、状态行）的 rect 在零视口下仍然有意义（块布局给了宽度），所以登录表单显隐断言可信；只有 fixed/transition 相关的量具失效。

## 2026-07-21 录演示视频踩的三个坑：PowerShell 读脚本的编码、localStorage 不随库重置、以及自动化只认已安装程序

录 `Solum_demo_v3.mp4` 时踩的，都不涉及产品代码，但下次再录会原样再踩一遍。

- **PowerShell 5.1 把无 BOM 的 UTF-8 脚本按 ANSI 读，中文字面量全成乱码，而且脚本正文被粘进了应用**
  - **现象**：第一条 165s 的录制全废。画面里聊天框先出现 `鏄庡ぉ涓嬪崍3鐐?..`（"明天下午3点…"的 UTF-8-被读成-GBK 形态），紧接着**编排脚本自己的注释和代码被整段粘进输入框并发送出去**。
  - **根因**：编排脚本用 UTF-8 无 BOM 写盘，PowerShell 5.1 默认按系统 ANSI 码页解析脚本文件。中文字面量当场变乱码；更糟的是乱码破坏了引号配对，后续行被并进同一个字符串参数，于是 `Set-Clipboard` 收到的是脚本正文。
  - **解决**：**编排脚本一律只用 ASCII**，所有非 ASCII 输入文本放进单独的 `strings.txt`，用 `Get-Content -Encoding UTF8` 显式读回。（写 BOM 也能解，但"脚本纯 ASCII + 数据外置"对下一个人更难写错。）
  - **判据**：只要一个 PowerShell 脚本里出现非 ASCII 字面量，就先确认它的编码怎么被解释——**乱码不只是显示问题，它会改变脚本的语法结构。**
- **重置 SQLite 库并不会重置聊天记录，因为会话存在 localStorage 里**
  - **现象**：删掉 `demo.sqlite` 重新喂数据、重启应用，界面上仍然挂着上一轮排练的会话列表和那条组件预览。
  - **根因**：`pa.chat-sessions.v1` 是 **localStorage 键**（改名时刻意保留的旧键之一），归 WebView2 用户数据目录管，跟 `SOLUM_DB` 完全无关。
  - **解决**：给演示单独开一个 WebView 配置目录——启动前设 `WEBVIEW2_USER_DATA_FOLDER` 指向临时目录。**刻意没有去删 `%LOCALAPPDATA%\dev.solum.app\EBWebView`**：那是 bundle id 级别的共享目录，删它会连带清掉用户真实使用中的会话历史。隔离比清理安全。
  - **判据**：「重置演示环境」要同时想到**两套持久化**——Rust 侧的 SQLite 和 WebView 侧的 localStorage/IndexedDB（后者还有 `pa-local-documents-v1`）。只重置一套，界面会带着上一轮的残留出镜。
- **桌面自动化只能驱动"已正式安装"的程序，`cargo build` 出来的 exe 驱动不了**
  - **现象**：授权接口对 `Solum` / `息壤` / `solum-app` / 窗口标题全部返回 "doesn't match any installed or running application"，尽管进程就在跑、窗口标题清清楚楚。
  - **根因**：解析器按开始菜单已安装程序清单匹配，且清单在会话启动时快照。往开始菜单丢一个 `.lnk` 快捷方式也没用——当前会话的清单已经定型。
  - **解决**：绕开该通道，改用 PowerShell 直接做——`System.Drawing` 抓窗口矩形截图、`user32.dll` 的 `SetCursorPos`/`mouse_event` 点击、`SendKeys` + 剪贴板输入。`GetWindowRect` + `MoveWindow` 把窗口钉在固定位置，坐标才能在多次运行间复用。
  - **判据**：要驱动**未安装的本地构建**时，别在授权通道上耗时间，直接走 Win32。顺带一提，截图只截窗口矩形而不是整屏，桌面上其他窗口就不会混进演示素材。

## 2026-07-21 幂等 receipt 配了个"按龄清理"，等于把刚堵上的洞又开回来；以及我的回归测试在错误实现下照样全绿

- **现象**：上一轮补的 receipt 被用户拒签收。receipt 本身没问题，问题是 drain 每轮还跑 `prune_capture_loss_receipts(now - 30d)`。
- **根因**：**给幂等 guard 配了一个和它守的窗口无关的过期条件。** receipt 守的是「记账成功 → 删文件」之间的崩溃窗口，我默认这窗口是「一个 drain tick」，所以 30 天"绰绰有余"。但删除失败（只读卷、被占用、权限变更）时 marker 会**无限期**留在盘上——这窗口根本没有上界。于是任何 cutoff 都排出同一个顺序：receipt 先过期 → marker 后重扫 → 再次累加，总数高于真实值。
  - **最难堪的是源码注释当时就写着**「pruning one whose file somehow still exists would let it be counted a second time」——风险写明白了，代码照做不误。同一轮里 `undeliverable` 的说明也点了同样的机制，但只对 `failed/` 改成实况清点，marker 这条漏了。
  - 判据：**幂等 receipt 的退休条件必须是「它守护的那个东西确实没了」，不能是时间。** 时间是个和不变量无关的代理量；只要真实窗口没有上界，任何 cutoff 都是错的。宁可泄漏几行（几个字节、不失真），也不要按龄清理（会失真）。
- **比技术点更该记的：我写的第一版回归测试，在错误实现下也是绿的。**
  - 我照例做退化验证（把旧的按龄清理加回去重跑），结果 **16 条全过**。原因是 prune 在同一个 tick 里排在计数**之后**，而测试里的 marker 每次都删除成功——单次 drain 永远走不到「receipt 没了但文件还在」那一格。测试写的是我脑子里的故事，不是那条失效路径。
  - 改法：**必须构造出「删除持续失败」**。用一个名为 `*.mark` 的**目录**当 marker——`remove_file` 在任何平台上都删不掉目录，而普查只按扩展名过滤，照收不误。再跑两个 tick。改完之后旧实现如期挂掉（`left: 2, right: 1`，一个 marker 数了两次）。
  - 判据：**退化验证不是走过场——先把正确实现换成错的，确认测试真的挂，再谈"测过了"。** 而且要挂在你声称修的那条路径上。绿灯只证明新代码能跑，不证明测试钉得住回归。
  - 连带判据：**模拟崩溃要模拟"那一步没发生"，不是"事后把现场恢复成那样"。** 旧的迁移测试是"删成功之后再把文件写回去"——在新模型下那是一笔**全新的 tally**，计数是对的，测试等于什么都没测。改成直接记账、不删、留着文件。
- **解决**：`prune_capture_loss_receipts(before)` → `release_capture_loss_receipts(&[receipt])`，按名删；调用方一律「先删文件 → 确认不存在（`NotFound` 也算） → 再释放 receipt」。副作用：稳态下表反而更小了（以前要压 30 天的行，现在当轮就释放）。

## 2026-07-21 用宽松断言把已知缺陷"合理化"，以及把状态误当成事件

- **现象**：溢出计数的 marker 方案交出去后又被打回。问题是「记账成功、删文件前崩溃 → 下次重扫重复计数」。而我当时**知道这件事**——测试里写的是 `assert!(count >= 1)`。
- **最该记的不是技术点，是这个动作本身**：我写了一条宽松断言把已知缺陷固化成"预期行为"，同时实现注释还写着 `never counted twice`、界面还在说「至少 N 条」。**三处说法互相矛盾，而矛盾是我自己造的。**
  - 判据：**当你要为一条断言放宽条件时（`>=` 而不是 `==`、`is_ok()` 而不是查值），停下来问「我是在描述正确行为，还是在给已知缺陷让路」。** 后者的信号很明确——你能说出它在什么情况下会不成立。
  - 连带判据：**注释、测试、UI 文案三者对同一性质的说法必须一致。** 不一致时，最强的那个（这里是 UI 的「至少 N」= 下界承诺）就是你实际欠下的债。
- **技术上的正解**：数据库提交与文件删除跨两个系统，天然不原子。要么做**幂等 receipt**（同一事务内插入唯一键 + 累加，重扫不重复），要么把产品语义降级成「检测到发生过丢弃，数量不保证」。**不能既不做 receipt 又展示「至少 N」。**
- **交付前自查又挖出一条同源的错误：把「状态」当成「事件」来记。**
  - `failed/` 目录里的文件是**永久保留**的，我却给它配了一个事件计数器。两头都错：drain 的 `read_dir` 不递归，扫不到 `failed/`，所以 rename 后崩溃那笔永远不会被计数；而 receipt 30 天后被清理，同一个还在盘上的文件又会被重复计数。
  - 正解是**别记账，现场清点**。判据：**如果被计数的东西会一直留在那儿，就不要维护计数器——查询时数一遍。** 从事物本身导出的答案不可能和事物漂移；独立维护的计数一定会。计数器只适合"计完就消失"的事件（这里是被删掉的 marker）。

## 2026-07-21 跨进程共享可变文件：连修四版都没修对，最后靠换掉数据结构才解决

- **现象**：一个「被丢弃通知的计数器」，被复审连着打回四次。v1 读-改-写；v2 加进程内 `synchronized`；v3 改 append 一字节 + 读端 rename 认领；v4 才对——**把共享计数文件整个换成一次事件一个不可变 marker 文件**。
- **每一版被打回的原因，是同一个竞态换了个位置**：
  - v1/v2：读端读到 `n`，写端写出 `n+1`，读端删文件 → 新增那次没了。进程内的锁完全管不到另一个进程。
  - v3：append 消掉了「过期总数覆盖」，但**没消掉在途描述符**——写端已 `open` 旧 live，读端 rename + 读 + unlink 之后，写端的 `write` 才落地，落在孤儿 inode 上。`fsync` 无用，因为描述符在 rename 前就绑定了。
- **真正的教训**：**只要两个进程共享一个可变文件，"加锁 / 加 rename / 加 fsync" 都只是在挪窗口**。我连着三版都在优化协调手段，而正确的动作是**换掉数据结构**——变成一次事件一个不可变文件之后，没有共享可变状态，也就没有需要协调的东西。
  - 判据：**跨进程状态优先设计成「只追加不可变对象 + 读端只删自己数过的」**，而不是「共享可变值 + 想办法同步」。前者不需要任何跨进程原语；后者在没有文件锁的情况下基本做不对。
  - 配套的红线：读端**只能删除它明确数过的那些路径**。图省事按目录重新列举来删，会把这个设计的全部好处一次性抵消。
- **测试上的教训（这条同样丢人）**：v3 我写了一条叫「drain 期间到达的丢弃不被吞掉」的测试，实际做的是「drain 完 → 写 → 再 drain」——**名字描述的是我想测的东西，代码测的是另一件事**，而且它当然是绿的。真正构造窗口需要显式分步：普查 → 此刻插入 → 只删普查到的 → 断言新的还在。
  - **判据：写完并发测试后，用「错误实现」跑一遍，确认它会挂。** 挂不了就说明测试没覆盖到它声称覆盖的东西。这次我照做了（用一段独立脚本验证「按目录重列举删除」的实现会丢 marker），才敢说这条测试是有效的。

## 2026-07-21 跨进程计数器：为什么「加把锁」和「加个 rename」都不够

- **现象**：给 spool 溢出加了计数（Kotlin `synchronized` 保护）、给队列加了上限。复审指出两者的并发正确性都不成立——计数会错报，上限会被突破。
- **坑一：锁只能保护同一个进程里的写者。** Kotlin 的 `synchronized` 管住了它自己的并发写，但 Rust 在**另一个进程**里做「读 → 入库 → 删除」。读到 `n` 之后原生写出 `n+1`，删除就把新增那次抹掉了。
  - **第一个直觉修法（rename 后再读）也不够**，这是最值得记的一点：Kotlin 那边是**读-改-写**。Rust 把文件 rename 走之后，一次在途的 RMW 仍会把它读到的旧总数写进新建的 live 文件——刚被认领的计数又回来了。**只要写者是 RMW，读者做什么都救不了。**
  - **正解是把写端变成没有读的操作**：一次丢弃 append 一个字节，计数 = 文件长度。没有读就没有过期。然后读端 rename 认领才真正成立。
  - 判据：**跨进程共享状态时，先问「写端是不是 read-modify-write」**。是的话，先把它改成 append/insert 之类的单向操作，再谈读端怎么同步；顺序反了会一直修不对。
- **坑二：把检查和它授权的动作放在两个临界区。** 锁只包了「已经满了之后记一笔」，没包「清理 → 计数 → 写文件」。于是多个通知可以同时看到 4 999 然后一起写。
  - 判据：**「检查配额」和「占用配额」必须在同一个临界区里**，否则那不是上限，是个建议。同类形态：先 `exists()` 再 `create`、先查余额再扣款、先看容量再入队。
- **附带一个测试写法上的坑**：崩溃恢复那条我最初断言「遗留的先记、live 的下一轮再记」，测试挂了——而**代码是对的**，一轮里把两者都记上不丢不重。我断言的是实现细节而非性质。**判据：断言应该写「总数正确且幂等」，而不是「分几轮完成」**——后者会在实现合理变化时假报警，反过来诱导你去改对的代码。

## 2026-07-21 「换个更好的设计」也会带进新洞：spool 改造自己丢数据的两种方式

- **现象**：把通知收件箱从「共享 JSONL 追加」改成「单通知单文件 spool」，这个方向是对的（并发追加确实无法做安全），但新实现被复审抓出两个 P2，**都是丢用户数据**。
- **洞一：给了上限，没给「越界了要让人知道」的通道。** 原生端到 5 000 文件就 `return`，没计数没提示。而且计数用的是 `list()`（含 `.tmp`），几个崩溃残留的临时文件就能永久占住配额——此后通知全丢，界面上完全看不出。
  - 这条和我三天前刚给自己写下的判据**一字不差**：「写下 `DELETE` 或 `LIMIT` 的同时就要想清楚『谁会因此少拿到东西，他怎么知道』」。**写下了，然后在下一个功能里又犯了一次。** 说明这类判据光记在文档里不够，得在改动清单里当成检查项过一遍。
- **洞二：注释写的是 A，代码做的是 B——同一个错误第二次犯。** 删除处的注释白纸黑字写着「核心接收之后才删」，而代码是 `if let Ok(Some(record)) = ...` 吞掉 `Err`、然后无条件 `remove_file`。数据库忙这类**可恢复**故障因此变成永久丢失。
  - 根因是把「核心决定不留」（`Ok(None)`：未授权、空文本）和「核心没能留下」（`Err`）当成了同一件事。前者是完成态，后者必须重试。**`if let Ok(..)` 这个写法本身就是气味**：它把错误分支静默成了「什么都不做」，而调用方往往假设「没报错 = 成功」。
- **如何避免**：
  - **`if let Ok(x) = ...` / `.ok()` / `unwrap_or_default()` 出现在「之后要做不可逆动作」的路径上时，一律停下来**：错误被吞掉之后，后面那个删除/提交/推进游标还成立吗？
  - **在结果类型里把「决定不做」和「没能做成」分开**（这里是 `Ok(None)` vs `Err`，落到 `IngestBatch { outcomes, failed }`）。靠调用方记住区别是不可靠的，让类型替你记。
  - **重试必须有界。** 无界重试是毒丸的另一种写法——我在同步那边刚修过，这里差点原样再来一遍。有界之后要保留数据（移入 `failed/`）并计数，而不是删掉。

## 2026-07-21 安全审核修复期五连坑：量具连挂两次、把一步提前踩了顺序依赖、「夹回合法值」不等于修好、批量替换打中同形状的另一个类型、白名单抄错了来源

> 背景：按外部安全审核报告逐条修复（P1 13 项 / P2 19 项 / P3 5 项）。下面五条都是**改的过程中**踩的，不是被审核指出来的问题本身。

### 坑一：mock-IPC 走查里量具连挂两次，差点判定"应用坏了"（量具类，最值得记）

- **现象**：给三处删除改走 Guard 之后做真浏览器走查，页面静态内容渲染正常，但 `askForget` / `guardedDestructive` 全是 `undefined`，一次 IPC 都没发出。看起来像整个内联脚本没跑。
- **根因（两个，叠在一起）**：
  1. 我的 `mock.js` 在顶层写了 `async function invoke(...)`，而 `dist/index.html` 自己有 `const invoke = window.__TAURI__...`。**同名重复声明 → 整个内联脚本 SyntaxError**，一行都不执行。
  2. 包进 IIFE 修掉之后仍然不动。这次是我那个 20 行静态服务器：`req.url === '/' ? '/preview.html' : req.url.split('?')[0]`，于是 `/?v=2`（我加的缓存穿透参数）走进 else 分支，`split('?')[0]` 得到 `/`，`readFile` 读一个目录 → 404。**页面根本没加载，我却在断言页面的行为。**
- **解决**：mock 整体收进 IIFE，不向全局泄任何标识符；访问改用显式路径 `/preview.html?v=N`。
- **如何避免**：
  - **harness 不许向全局泄标识符**——被测页面是 vanilla JS 全局作用域，任何顶层 `function`/`const` 都可能与它撞名，而撞名的表现是"整个脚本静默失效"，看起来像功能坏了。mock 一律 IIFE + 只挂 `window.__XXX__` 命名空间。
  - **先证明量具本身是活的，再用它做断言**。这次的正确顺序是：第一条断言应该是 `window.__errs`/`typeof someKnownGlobal`，确认 harness 和页面都起来了，再谈功能。
  - AGENTS.md 那句「看到与预期相反且过于干脆的结论（"完全没渲染"、"三种条件结果一模一样"），先怀疑量具」——这次是现场复现，而且**连挂两次**：修好第一个之后现象没变，很容易误判成"看来真是应用的问题"。**量具可以同时坏在多个地方。**

### 坑二：把一步提前，踩了后续步骤对"它还没发生"的隐式依赖

- **现象**：改 `AlarmScheduler.replaceAll`，为了让"写盘失败就不动已挂载的闹钟"，把 `save(ctx, items)` 提到取消循环之前。改完自己读了一遍才发现是错的。
- **根因**：取消循环是 `for (old in load(ctx)) am.cancel(...)`——它靠 `load()` 读**旧**集合。`save` 一提前，文件已经是新集合，循环就会去取消新闹钟、而真正该取消的旧闹钟留在系统里。原代码的正确性隐含依赖"此刻文件还是旧的"，这个依赖没有任何注释。
- **解决**：先 `val previous = load(ctx)` 存进局部变量，再 save，再按 `previous` 取消。
- **如何避免**：**调整语句顺序时，逐条检查后续语句是否在读被移动那步所写的状态**。判据：一个函数里如果同时存在"读某处"和"写同一处"，它们的相对顺序就是契约的一部分，重排前先把读结果固化到局部变量。这类 bug 编译器不报、测试也未必覆盖（Kotlin 侧本就没有自动化测试）。

### 坑三：把非法值「夹回合法范围」不等于修好了

- **现象**：修"导入备份用 `exported_at` 当 LWW 时间戳、伪造成 2099 就能永久压过本机数据"。第一版做的是 `stamp = min(exported_at, now)`——把未来夹回现在。写完回归测试，断言"伪造的备份不该压过本机较新的编辑"，**测试挂了**。
- **根因**：夹回 `now` 之后，这份备份的**内容是旧的、时间戳是新的**，于是它照样压过导入之前的所有本地编辑。夹值只消除了"永久无敌"，没消除"不该赢却赢了"。
- **解决**：改为**直接拒绝**导入。文件要么是诚实备份（时间戳本就在过去，什么都不用修），要么不是——不是就该说出来，而不是猜一个修法。
- **如何避免**：**当一个修复的形式是"把非法输入改成合法输入"时，必须再问一句：改完之后的语义是不是用户想要的？** 很多时候正确答案是拒绝而不是修正——尤其当输入是不可信来源、而"修正"会让它以一个看似正常的身份继续参与竞争时。这条也是测试救的场：如果只读代码不写断言，clamp 版看起来完全合理。

### 坑四：批量文本替换打中了同形状的另一个类型

- **现象**：给 `ActionProposalState` 加 `Stale` 变体，用 python 做三处 replace（enum 定义 / `as_str` / `FromStr`）。编译报错说 `ActionProposalState` 没有 `Stale`。
- **根因**：同一文件里 `FilterProposalState` 也是 `Pending / Accepted / Dismissed` 三个变体、`as_str` 与 `FromStr` 也是同一形状，且**出现在前面**。`str.replace(a, b, 1)` 全部命中了它。编译错误指向调用点（"ActionProposalState 没有 Stale"），完全没提示"你改错类型了"——错误信息把注意力引到了正确的地方，反而掩盖了改动落错位置这件事。
- **解决**：`git diff` 逐块核对改动落点，回滚错的三处，用带上下文的更长锚点重做。
- **如何避免**：**在同一文件里做"按形状"的批量替换前，先确认这个形状是不是唯一的**（`grep -c` 一下锚点）。以及：**改完立刻 `git diff` 看落点，不要用"编译过了/编译错在哪"当落点是否正确的证据**——编译器检查的是引用一致性，不是你有没有改对地方。

### 坑五：白名单抄了一个"看起来相关"的常量，而不是抄产出端

- **现象**：给导入加"拒绝未知表"，白名单直接用了 `SYNCED_TABLES`。跑测试，四个既有的导入测试全挂：`备份里含有本机不认识的表 meta`。
- **根因**：`_restore` 段由 `export_restore_rows()` 产出，它写的是 `SYNC_PAYLOADS` 的每张表**外加 `meta`**（以 LWW 文档形式同步的配置键——没有它，还原出来的设备会丢掉规则表）。`SYNCED_TABLES` 是另一个用途的常量，名字像但内容不是一回事。
- **解决**：白名单改为 `SYNC_PAYLOADS.iter().any(...) || tbl == "meta"`，也就是以导出端实际写出的东西为准。
- **如何避免**：**校验"允许出现什么"时，判据要取自产出端，不是取自一个名字听起来对的常量。** 问法是"谁写出这段数据，它会写哪些"，不是"哪个常量看起来是这个清单"。这次是既有测试挡住的——它们本来就在测正常备份能还原，正好覆盖到了。

## 2026-07-21 Android 打包三连坑：native-tls 在 Android 上没有出路、改名遗留全藏在 gitignore 的生成文件里、msys PERL5LIB 被驱动器冒号切碎

- **背景**：更名 PA → Solum（7-20）之后**从没跑过 Android 构建**，加上当天并行落地的邮箱连接器，本次打包一次性引爆了三类问题。

### 坑一：`native-tls` 在 Android 上是死路，且 Git 自带 perl 补不动

- **现象**：`cargo ndk ... build` 直接失败 `Could not find directory of OpenSSL installation`。
- **根因**：邮箱连接器用 `imap 2.4.1 + native-tls`，`native-tls` 在非 Apple/Windows 平台一律走 `openssl-sys`；**Android 没有系统 OpenSSL**，只能 vendored 从源码交叉编译。
- **走过的弯路（值得记，因为看着每一步都快成了）**：加 `openssl = { features = ["vendored"] }` → openssl-src 调 perl 的 `./Configure` 失败，Git-for-Windows 的 perl 是**精简版**，缺 `Locale::Maketext::Simple`；补完这个又缺 `ExtUtils::MakeMaker`（大件，无法用 shim 糊）；期间还发现 **`cpan` 自身也残缺**（缺 `CPAN::Author`），装不了模块。**判据：当一个环境要你连补三个本该是 core 的模块时，那不是"差一步"，是这个环境不适合干这件事**，该换路线而不是继续补。
- **解决**：迁到 **rustls**（纯 Rust，交叉编译零外部依赖）。`imap` 必须同时升到 3.0.0-alpha.15（2.4.1 无 rustls feature），API 迁移面仅三处，见 CHANGELOG 当日条目；`lettre` 只换 feature、代码不动。
- **避免**：**给要上 Android/iOS 的 Rust 项目选依赖时，先查它的 TLS 后端**——`native-tls` 在移动端等于 OpenSSL 交叉编译，`rustls` 才是默认应选项。这条要在**引入依赖时**查，不是等打包时才发现。

### 坑二：改名遗留全在 `.gitignore` 里的生成文件中，`git status` 干净但 Android 根本编不过

- **现象**：修完 TLS 后 gradle 依次报 ①Kotlin 编译错（`TauriActivity` 找不到）②`No matching variant of project :pa-health-connect`。
- **根因**：`cargo tauri` 生成的四类胶水文件全部停在旧名，而它们**都被 gitignore**（正常应由 `cargo tauri android init/build` 重新生成），本机没装 cargo-tauri，于是改名脚本没碰、git 也不报：`generated/*.kt` 九个文件仍 `package dev.pa.app`（与目录 `dev/solum/app/` 不符，`MainActivity` 靠同包解析引用基类直接编译失败）；`Rust.kt` 仍 `loadLibrary("pa_app_lib")`（crate 已产出 `solum_app_lib`，编过也会 `UnsatisfiedLinkError`）；两个 `.pro` 的 `-keep` 仍指 `dev.pa.app.*`（**release 开着 minify**，R8 会把 WebView/Ipc 剥掉——「构建成功但一跑就崩」）；`tauri.settings.gradle` / `tauri.build.gradle.kts` 仍引用 `:pa-*` 三个插件工程。
- **避免**：**大规模改名后必须把每个目标平台都真构建一遍才算完**——`git status` 干净不代表改完了，生成物/被 ignore 的文件是改名脚本和 code review 的双盲区。判据：**凡是「工具生成、进 gitignore」的文件，改名时都要单独列清单人工过一遍**，或在有该工具的机器上重新生成。另：`isMinifyEnabled = true` 的 proguard 规则错误**不会让构建失败**，只会让运行时崩——这类"沉默的错"要专门找。

### 坑三：给「关一个浮层 + 开另一个浮层」各自配对 history，会被 `history.back()` 的异步性反杀

- **现象**：为让 Android 返回键关浮层而不是退出应用，给抽屉/模态/菜单各自 `pushState` / `back()` 配对。真机上「点输入框 + → 点组件库」，抽屉**闪一下就没了**，表现像"点了没反应"。
- **根因**：菜单项的 onclick 先 `toggleComposerMenu(false)`（→ `history.back()`）再 `openDrawer()`（→ `pushState`）。**`history.back()` 不是同步的**，它的 popstate 在当前任务跑完之后才派发——那时抽屉已经开好，于是这条延迟的 popstate 按"关最顶层浮层"的逻辑把抽屉关掉了。计数是平的，顺序是错的。
- **解决**：不按浮层个数计数，只维护**「当前有没有浮层」这一条 history**；状态变更后不立即比对，而是 `queueMicrotask` 里比对一次——同一轮里的「关 A + 开 B」到微任务执行时已经落定为「仍有浮层」，什么都不用做。
- **避免**：**只要一次交互里会「关掉一个浮层同时打开另一个」，就不要给浮层各配一条 history**。判据：`history.back()` / `pushState` 与 DOM 状态的同步，必须放在"这一轮所有状态改动都完成之后"的时点（微任务/`requestAnimationFrame`），否则中间态会被当成终态。同类陷阱适用于任何"关闭时做副作用"的浮层管理（焦点归还、滚动锁定同理）。

### 坑四：msys perl 的 `PERL5LIB` 被驱动器盘符的冒号切碎（量具类，通用）

- **现象**：把补丁模块放进 scratchpad 并 `export PERL5LIB="C:/Users/.../perllib"`，perl 仍报找不到；打印 `@INC` 看到两条垃圾项：`C` 和 `/Users/.../perllib`。换成 msys 风格 `/c/Users/...` 后，从 bash 直接调 perl 正常，但**被 Rust build script（原生 Windows 进程）拉起时又失败**。
- **根因**：msys perl 按 Unix 惯例用 **`:` 作 PERL5LIB 分隔符**，`C:/...` 于是被切成两段；而 msys 的 bash 在把环境变量传给原生 Windows 子进程时会把 `/c/...` **自动转回 `C:/...`**，于是绕回同一个问题——**没有任何环境变量写法能同时满足两端**。
- **解决**：放弃环境变量，把模块装进 perl 本就搜索的 `site_perl`（`/usr/share/perl5/site_perl/`，这正是该目录的用途）。事后随路线切换已删除。
- **避免**：msys/Windows 混合环境里，**带盘符的路径不要放进任何用 `:` 分隔的环境变量**（`PERL5LIB`、`CLASSPATH` 的 Unix 形式等）。判据：设完先打印程序实际看到的解析结果（`perl -e 'print join("|",@INC)'`）再往下走，别假设 export 成功就是生效。

## 2026-07-20 关闭的 `<details>` 里，`getBoundingClientRect` / `offsetWidth` 全是非零——新 Chromium 用 content-visibility 藏内容，几何量具集体失效

- **现象**：UI 重构给人格页「聊天记录导入」套上默认关闭的 `details.fold` 后，走查断言「收起时内容不可见」失败：`open === false`，但内部按钮 `getBoundingClientRect()` 高 38px、`offsetWidth` 非零、`getClientRects().length > 0`，`.fold-body` 量出 312px 高——按本仓「断言落在渲染结果上」的惯例，这三件量具都说"内容在屏"。
- **根因**：新版 Chromium 的 `<details>` 收起不再走 `display:none`，而是 UA 样式 `::details-content { content-visibility: hidden }`。这种隐藏**保留布局盒**（所以所有几何 API 返回真实尺寸），只是跳过绘制与命中测试。也就是说 AGENTS.md 已记的「`offsetParent` 对 fixed 元素恒 null」之外，几何量具又多了一个反向失效面：**这次是"量出可见"的假阳性，而不是"量出不可见"的假阴性**。
- **解决**：对 `<details>`（以及一切可能被 content-visibility 藏起来的内容）改用两件不受布局盒欺骗的量具：① 祖先容器的 `innerText` 是否包含目标文案（content-visibility 隐藏的文本不进 innerText）；② `document.elementFromPoint(矩形中心)` 是否命中目标（跳过命中测试则必不命中）。两证齐了才下结论。
- **避免**：几何非零 ≠ 用户看得见。判断可见性的量具按隐藏机制选：`display:none` 看 rect；`opacity/visibility` 看 computedStyle；`content-visibility`（含关闭的 `<details>`）看 `innerText` + `elementFromPoint`。拿不准隐藏机制时，直接用后两件，它们对三种机制都成立（唯一例外：`pointer-events:none` 的元素不能用 elementFromPoint，AGENTS.md 已记）。

## 2026-07-20 改名两坑：Windows 上一个资源管理器窗口能挡住整棵目录树的重命名；Android 改包名等于放弃机上数据

- **现象**：PA → Solum 改名时 `git mv crates/pa-app crates/solum-app` 报 `Permission denied`，其余 6 个 crate 全部成功。重试仍失败。查进程只找到 Chrome、Codex、DevEco 的 hvigor 守护和 Google Drive，没有一个明显该占着这个仓库。
- **根因**：逐层试探（对每个子目录试 `Rename-Item` 再改回）定位到 `gen/android/app/build/outputs`。**该目录下每个文件都能独占打开**（`[System.IO.File]::Open(..., 'None')` 全部成功）——锁的不是文件，是**目录句柄本身**。真凶是一个停在 `outputs\apk\universal\release` 的资源管理器窗口（当天 16:20 出完 release APK 后开着取包）。Windows 上一个打开的目录会一路阻止其**所有祖先**被重命名。
- **解决**：用 COM 把那个窗口导航走（`(New-Object -ComObject Shell.Application).Windows()` 枚举，`$w.Navigate(其他路径)`），不必关窗口，句柄立即释放，`git mv` 随即成功。
- **避免**：Windows 上目录重命名失败先别去杀进程。判据是**「文件都能独占打开但目录改不了」= 有人拿着目录句柄**，而资源管理器窗口、终端的当前工作目录、文件监视器都会这样，它们在进程列表里毫不起眼。逐层试探比猜进程快得多，`Shell.Application` 枚举能直接看到资源管理器停在哪。**顺带一个 PowerShell 坑**：`catch` 块里 `$_` 是 ErrorRecord 不是循环变量，`"LOCKED $($_.Name)"` 会打出空名字——先把循环变量存成具名变量再用。
- **第二坑（推演出来的，不是撞上的）**：改 `applicationId`（`dev.pa.app` → `dev.solum.app`）后，装在手机上的旧版**是另一个 App**，其私有目录新包根本读不到。所以 `adopt_legacy_db` 在 Android 上**必然是空操作**，写它的时候要清楚这一点，别以为加了迁移代码手机就自动接上了。真实路径只有**旧版导出 → 装新版 → 导入**。这也意味着改名窗口越早越好：机上数据越多，这条手工路径越疼。

## 2026-07-20 浏览器走查的两个新量具陷阱：后台标签页冻结动画、px 字号不随根字号缩放

- **现象**：390px 组件页走查里连续两次得出错误结论。① 组件视图测出 `opacity: 0`，看着像「整页渲染了但用户看不见」；② 把根字号从 16px 拉到 24px 模拟大字体，**四档缩放下表格宽度、磁贴宽度一个像素都没变**，一度要写成「布局对字号完全不敏感」。
- **根因**：① 受控浏览器的标签页 `document.visibilityState === "hidden"`，CSS 动画被冻结在第 0 帧——`.vwrap` 的 `viewin` 入场动画正是从 `opacity: 0` 起步且 `animation-fill-mode: none`，于是 `getComputedStyle` 永远读到起始帧。实测 `getAnimations()[0]` 是 `playState: "running"` 但 `currentTime: 0`，这个组合就是「被冻住」的签名。② 本仓 CSS 的字号全是 `px`（`.wtable` 13px、`.statlabel` 12px、`.statnum` 22px），**改 `html` 的 `font-size` 对 px 声明毫无作用**，那个测试实际上什么都没测。
- **解决**：① 采样前先 `document.getAnimations().forEach(a => a.finish())`，测稳定帧而不是入场帧（改完 `opacity` 立刻是 1）。② 改用 `-webkit-text-size-adjust: N%` 模拟 Android WebView 的 `textZoom`——它会缩放 px 文本，这才是真机上系统字号真正的作用路径。换对之后 `statnum` 22px→44px、表格 588→1056px，测试才开始有信息量。
- **避免**：**每次采样前先问「我这个量具会不会在这个环境下失效」**，两条通用判据：动画/过渡类断言，先确认标签页可见性与 `currentTime`；字号/缩放类断言，先确认**被测样式用的单位会不会响应你拧的那个旋钮**——拧之前先量一个探针（本次是 `getComputedStyle(.statnum).fontSize`），探针不动就说明旋钮没接上。
- **顺带（本轮第三、四次量具误报）**：两次的形态与既有条目完全一致——**结论过于整齐**（「四档缩放完全一样」）或**过于干脆**（「整个视图不可见」）。另外还栽了一次同源的：第一次采样用 `document.querySelector(".tscroll")` 取到的是**隐藏视图里**的同类元素（宽 0），因为全站多个视图共用这个类名且都在 DOM 里。**选择器要锚定到当前视图容器**（`#widgetsBox .tscroll`），别全局取第一个。

## 2026-07-20 给同步表加列时，列加了、触发器 payload 没加——功能在本机完美、跨设备静默消失

- **现象**：第三步刚交付的 `table` / `stat` 视图，在单机上怎么测都对（渲染、聚合、CLI、导出可读层全绿，234 个测试全过），但真机双设备走查一同步就没了：A 上四个视图的组件到了 B 只剩 form/list。同时两台设备的字段顺序莫名不一致（A `move,feel,weight,notes` / B `notes,weight,move,feel`）。
- **根因**：`widget_fields` 的 `SYNC_PAYLOADS` 只有 `form_ord` / `list_ord`。第三步加 `table_ord` / `stat_ord` 时改了建表、改了 `WidgetViewType::ALL`、改了渲染、改了 `apply_one` 的**接收**分支，唯独没改**发送**的 `json_object`。接收端读 `payload.get("table_ord")` 拿到 `None` 就落列默认值，于是「成功应用、无报错、数据安静地少一半」。连 v13 专门为跨设备顺序一致而加的 `ord` 也一直没进 payload——那一列从落地起就没真正生效过。
- **为什么测试没拦住**：既有的 `concurrent_field_additions_on_two_devices_merge_as_a_union` 只断言字段**名字**到齐（`names.contains("feel")`），没断言视图成员、没断言顺序。**并集语义是对的，被漏掉的是「行本身带没带够信息」**，而只查名字的断言对这类缺失完全失明。
- **解决**：payload 补 `ord` / `table_ord` / `stat_ord`；新增断言四个视图的字段列表与 `sort_by` 在对端逐一相等的测试；导出测试补断言 `_restore.widget_fields` 五个槽位键在场。存量靠 v15 迁移重播修复（只重播偏离默认值的行，见下条）。
- **避免**：**同步表新增任何一列，检查表是四处不是两处**——建表 / 迁移 `ALTER` / `SYNC_PAYLOADS` 发送 / `apply_one` 接收。前两处不做整个功能就跑不起来，所以永远不会忘；后两处漏了**本机功能完全正常**，只有另一台设备能发现，而它不会报错。判据很直接：**这一列的值，另一台设备有没有办法知道？** 没有就必须进 payload。`_restore` 与同步共用这份定义，所以漏一列同时意味着「备份也还原不回来」——**一处遗漏，两个出口一起塌**。
- **顺带（存量修复的形状）**：补完 payload 只对**将来**的写入生效，已经同步出去的坏行不会自己变好。重播时不能无差别 touch 全表——只收到过坏行的设备手里全是默认值，它一广播就会把自己的坏数据按 LWW 盖回好的那份。正确的判据是**只重播偏离默认值的行**：那恰好是本机权威的那批，纯接收方因此天然沉默。这条判据可复用于任何「payload 补列后修存量」的场景。

## 2026-07-20 迁移不在事务里 + 目标表有唯一索引 = 中途挂掉后数据库永久打不开

- **现象**：推演 v12 → v13 时发现，`migrate_widget_schema_to_rows` 把 schema 拆成行是逐条 `INSERT`（autocommit），最后才 `DROP COLUMN schema_json`。若进程在两者之间死掉（手机 ROM 清后台、断电），已插入的行**已提交**，而 `schema_json` 还在。下次打开 `migrate()` 从头重跑，`has_column("schema_json")` 仍为真 → 重新插同名字段 → 撞 `UNIQUE(widget_id, name)` → `Store::open` 直接报错。实测构造该状态后连开两次，**都是同一个错，没有任何自愈路径**——app 从此打不开。
- **根因**：两个各自合理的设计叠加。① 迁移步骤为了「可重入」用了 `IF NOT EXISTS` / `has_column` 这类幂等守卫，于是默认整个 `migrate()` 重跑是安全的；② 但**「重跑安全」要求每一步自身是幂等的**，而「读一列、展开成多行、再删掉那一列」这一步**只有在删列成功后才幂等**。中间态恰好是幂等性失效的窗口，唯一索引把「重复插入」从静默变成致命。
- **解决**：整段包一个 `unchecked_transaction`，字段行与 `DROP` 同生共死；失败即回滚回 v12 形状，后续版本还能重来。
- **避免**：**任何「先派生新数据、再删除数据源」的迁移，必须整段在一个事务里**——这类步骤的幂等性依赖于最后那一步，而最后一步没跑到正是崩溃最可能停下的地方。快速判据：**在这一步的每一行之间插入一次「进程被杀」，下次启动还能恢复吗？** 顺带记账：本仓 `migrate()` 整体仍非事务性（多个 `execute` 顺序执行），本次只收口了最尖锐的一处；其余步骤靠 `IF NOT EXISTS` 幂等守卫，暂未发现同类致命组合，但没有系统性证明。
- **顺带**：这条是**推演出来再复现**的，不是线上炸出来的。当前暴露面其实是零——手机 APK 停在 v6（早于 F19，根本没有组件数据），桌面库已经是 v14，全仓没有任何 v12 库。**「暴露面为零」不等于「不用修」**：v6 → v14 会一次性走完包括这步在内的八段迁移，而手机正是最容易被系统杀死的环境。

## 2026-07-20 `offsetParent === null` 对 fixed 元素恒为真，会把好功能误判成坏的

- **现象**：走查「提为日程」时判定"点了没有任何反馈、toast 没出现"，一度当成 bug 去查 handler。实测 handler 正确、无 console 报错。真相是量具错了两层：① 我用 `.toast` 选择器，而 toast 是 `id="toast"` 的单例节点；② 换对选择器后仍报"不可见"，因为可见性判据里写了 `offsetParent === null`——而 **`position: fixed` 元素的 `offsetParent` 永远是 `null`**。实际状态是 `.show` 在、`opacity: 1`、262×63 在屏，完全可见。
- **根因**：`offsetParent` 返回的是最近的**定位祖先**，规范规定 fixed 元素直接返回 `null`（sticky 在部分情况下同理）。它只对"因 `display:none` 而不渲染"这一种隐藏有效，被当成通用可见性判据就会稳定误报。AGENTS.md §3 当时正把它列为推荐断言之一，等于把这个陷阱写进了项目准则。
- **解决**：AGENTS.md §3 补上适用边界——fixed / sticky 元素改用 `getComputedStyle` 的 `opacity` / `visibility` / `display` + 矩形是否在视口内；`elementFromPoint` 命中测试对带 `pointer-events: none` 的元素（toast 正是）也不适用。
- **避免**：**每个可见性判据都有它只适用的隐藏方式**，别混用：`display:none` → 查 `display` 或 `offsetParent`；`opacity:0` / `visibility:hidden` → 查对应计算值；移出视口 → 查 `getBoundingClientRect` 与视口的关系；被遮挡 → 命中测试（且元素不能是 `pointer-events:none`）。**写断言前先问"我预期它是怎么被藏起来的"**，再挑对应的判据。
- **顺带（本轮第二次同类）**：这是本次会话里量具第二次误报（前一次是 harness 状态跨调用污染，见下方条目）。两次的共同形态都是**结论异常干脆**——"完全没渲染"、"三种条件结果一模一样"。**过于整齐的否定结论，先怀疑量具再怀疑代码**；误报的代价是让人去改本来正确的东西，不比漏报轻。

## 2026-07-20 把"可独立演进的集合"塞进一个标量列，行级 LWW 会静默吃掉一半

- **现象**：F19 第一条竖切把整份 schema 存成 `widget_defs.schema_json` 一列。推演两台设备并发加字段（手机加 `feel`、桌面加 `notes`）：行级 LWW 整行覆盖，hlc 大的赢，**另一边的字段永久消失**；更坏的是丢失是双重的——手机上已填 `feel` 的记录还在，但 schema 里没这个字段了，`validate_record` 判它们含未知字段，**记录数据被 schema 孤儿化**。
- **根因**：LWW 的合并单元是**行**，而这一列里装的是一个**本可以逐元素独立演进的集合**。两者粒度不匹配时，同步不会报错、不会冲突提示，就是安静地少一半。这与 `local_only` 那条同源：**把两个独立变化的东西绑在一个存储单元上**，早晚要为"表达不了"付账。
- **解决**：schema 拆成一字段一行（`widget_fields`），合并即并集。关键是设计稿 ⑧「只允许加可空字段」让字段集合成为**只增集合（G-Set）**——只增集合的并集天然收敛，于是**不需要写任何新的合并代码**，现有触发器/guid/LWW 直接生效。演进约束和同步不是互相拖累，是互相成全。
- **避免**：**存进一个列之前先问"这里面的东西会不会各自独立地变"**。会，就拆行；这不是范式洁癖，是同步语义的先决条件。判据很实用：**能不能想出一个"两台设备各改一点、都该保留"的场景**——想得出就说明粒度错了。反过来，真正的标量（组件名、图标、list 的排序字段）留在行里走 LWW 是对的，不必一并拆。
- **顺带**：拆行后要额外给一列**显式顺序**（`ord`）。同一批插入的 `created_at` 完全相同，若靠 `(created_at, guid)` 排序就会落到随机 guid 上——**同一批行在两台设备上渲染出不同顺序**。这次是导出测试断言字段名顺序时才炸出来的，否则很容易一路带到线上。

## 2026-07-20 SQLite 的 FK 级联删除不触发子表触发器，会给对端留一地孤儿

- **现象**：`widget_records` / `widget_fields` 靠 `ON DELETE CASCADE` 跟着 `widget_defs` 走。两表不同步时完全正常；一旦进 `SYNCED_TABLES`，删除组件会在本机干净删除，却**不产生任何子行的 delete op**，其他设备永远留着那些字段和记录。
- **根因**：SQLite 的 FK 动作默认**不触发**其他触发器，除非 `PRAGMA recursive_triggers = ON`——本仓从未开启（`PRAGMA foreign_keys = ON` 是另一件事，两者常被混为一谈）。所以 `AFTER DELETE ON widget_records` 的同步触发器在级联路径上根本不会跑。危险之处在于**本机行为完全正确**，只有对端能看出问题，而对端不会报错，只是数据越攒越多。
- **解决**：`delete_widget_definition` 改为显式 `DELETE FROM widget_records` → `DELETE FROM widget_fields` → `DELETE FROM widget_defs`，每行各自产生 delete op。测试直接断言 oplog 里出现了 1 条 records + 2 条 fields + 1 条 defs 的 delete。
- **避免**：**同步表之间不要用 FK 级联做删除**——写路径要能被触发器看见，就必须是显式语句。§3.8 早就写着"变更捕获用触发器（含级联删除，Rust 写路径漏不掉）"，本仓既有同步表也确实都是 Rust 显式删的；这次是新表沿用了"本地表时代"的 FK 级联写法而没跟着改。**表从"本地"变成"同步"时，删除路径是必须重审的一项**，光加 guid 和触发器不够。
- **配套**：`ON CONFLICT(guid)` 需要 guid 上有 UNIQUE 索引，新同步表要记得加进那批 `CREATE UNIQUE INDEX ... ON x(guid)`，否则运行时报 "ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint"。同理，新表的插入要显式带 `new_guid()`——触发器的 `WHEN NEW.guid IS NOT NULL` 会把 guid 为空的行**静默跳过**，表现为"删了/改了但对端没反应"。

## 2026-07-20 按"文档声称"验收会漏掉"设计稿承诺过但从未被复述"的约束

- **现象**：Phase 11 第一轮验收对着 ARCHITECTURE §3.12 与 CHANGELOG 逐条核代码，结论"声称全部属实"。但设计稿（MISC 2026-07-19）⑥ 明写的三条硬上限里，「组件总数 ≤ 8」根本没实现——第一轮完全没发现。
- **根因**：两层叠加。① **实现层**：字段数、视图数能从单份 schema 判断，顺理成章落进 `WidgetSchema::validate()`；组件总数是**设备属性不是 schema 属性**，在校验器里没有自然落点，于是掉出了心智模型。② **验收层**：ARCHITECTURE 和 CHANGELOG 在复述上限时都只写了前两条——**文档忠实反映了代码，而不是忠实反映了设计**。于是"对着文档核代码"这个方法在设计→文档这一环已经断了，核得再仔细也只是在验证代码和文档自洽。
- **解决**：`MAX_WIDGETS = 8` 加在 `insert_widget_definition` 存储边界（不是校验器），任何调用方绕不过；撞上限照样写拒绝日志。ARCHITECTURE §3.12 补「硬上限」段，把三条并列写全。
- **避免**：**验收的输入不能只是"最新文档"，必须回到最初的设计稿/需求清单。** 文档是代码的下游——实现漏了什么，文档往往跟着漏同一样，两者自洽不构成证据。具体做法：设计稿里凡是**枚举形式的约束清单**（"三条上限"、"七类字段"、"四项补充"），验收时逐项打勾，不能只看后续文档的转述。**判据：如果一条约束只在设计稿里出现过一次、后续文档从未复述，它就是最可能被漏掉的那条**——因为没有任何下游文本会提醒你它存在。
- **顺带**：本次三条上限漏的恰好是唯一一条"无法从单份数据判断"的。这类**跨记录/跨设备的全局约束**天然没有局部落点，最容易在"每个函数都只管好自己"的干净设计里无家可归。写校验器时值得专门问一句：这批约束里有没有哪条不属于任何单个对象？

## 2026-07-20 harness 里连续改状态再采样：上一次失败的调用已经改了状态，导致误报 bug

- **现象**：走查 F19 组件页排序时，连续三次采样「按重量升序 / 降序 / 按动作」，DOM 行序**三次完全相同**，据此判定"排序 select 的值变了但列表不重排"，一度写进验收结论当成真 bug。实际上排序功能完全正常。
- **根因**：前一次 JS 调用在中途抛错（`s3[1]` 为 undefined）而中止，但它**在抛错前已经成功执行了两次 `dispatchEvent`**，把排序状态改成了 `move+desc`。下一次调用的三次采样全是在这个既成状态上做的：第一次采样前的"设为 desc"是 no-op（本来就是 desc），"设为 move"也是 no-op。三次采样看起来是三种条件，其实是同一种。**报错的调用不等于没有副作用的调用**，而单页应用的状态是跨调用累积的。
- **解决**：重写成每次断言前**显式设定完整状态**（字段 + 方向都写死，不依赖当前值），四种组合各采一次。结果：weight 升序 = 硬拉(60)/深蹲(82.5)、weight 降序反转、move 升序 = 深蹲/硬拉（拼音 shen < ying）、move 降序反转，全部正确。
- **避免**：**前端 harness 的每个断言都要自带完整前置状态，不要依赖"上一步把它设成了什么"**——这跟单元测试里每个 test 自建 fixture 是同一条纪律，只是浏览器里没有框架帮你重置。两条具体做法：① 一次 JS 调用里做完"设状态 + 采样"，别跨调用；② 采样结果里**连当前状态一起返回**（本次就是靠把 `sels().map(x=>x.value)` 一起打印出来，才发现三次采样的 state 是同一个）。断言只回答"渲染成什么样"，不回答"当时是什么条件"，就没法证伪自己。
- **教训的另一面**：这次是**误报**，不是漏报。但误报同样有代价——差一点把一条不存在的缺陷写进验收结论、让人去改本来正确的代码。**验证工具本身也需要被验证**：看到"三种条件结果完全一致"这种过于整齐的结果，第一反应应该是怀疑测试，而不是宣布发现 bug。

## 2026-07-20 不同步的表更需要导出，但恰恰最容易在导出里被漏掉

- **现象**：F19 的 `widget_defs` / `widget_records` 落地时加了建表、CRUD、渲染、Guard 删除、9 个测试，唯独没进 `export.rs`。Rust 测试全绿、clippy 零告警，没有任何信号提示这层缺失。
- **根因**：新增表时的心智检查表是围绕**同步**建立的——"要不要加 guid、要不要进 `SYNCED_TABLES`、要不要写触发器"。F19 对这三问的答案都是"不要"，于是这张表被归类为"什么都不用接"，检查表就此结束。但**导出和同步是两条独立的出口**，前者恰恰在后者关闭时才更重要。原有导出测试只断言「每层 key 在场」，空数组也能通过，所以就算当时加了 key 也测不出内容缺失。
- **解决**：`widget_defs` / `widget_records` 加入 `build_export`，定义连 schema 一起导出；新增断言落在实际内容上的测试。见 CHANGELOG 当日条目。
- **避免**：新增任何持久化表时，检查表要问**两个**出口而不是一个：**同步（`SYNCED_TABLES` / guid / 触发器）和导出（`export.rs`）**。而且两者是**反相关**的——越是决定"这张表不同步"，导出就越是这批数据唯一的逃生口，越不能漏。判据：**问"这台设备现在丢了，这批数据还存在于别处吗"**，答案是"不存在"就必须进导出。
- **顺带**：断言「集合层在场」而不断言内容的测试，对"层存在但永远为空"这类缺陷是完全失明的。凡是 `assert!(!doc[key].is_null())` 这种在场性断言，都要配一条真的写入数据再读回来的用例。

## 2026-07-19 合并循环里 `return Err` = 同步永久卡死（且伪装成"同步正常"）

- **现象**：设想场景——新版设备同步过来一条本版本不认识的表（如未来的 `widget_defs`），旧设备此后**再也收不到任何数据**，但它自己的改动仍在正常上传，UI 上看不出异常。实测复现：`sync_once` 返回 `Err(Invalid("unknown sync table widget_defs"))`，同 blob 里那条完全合法的 events 也没落地。
- **根因**：三个各自合理的设计叠加出的放大效应。① `apply_one` 的兜底分支 `other => return Err(...)`；② `apply_remote_ops` 把整批 op 包在一个事务里，一条报错**整批回滚**；③ `sync.rs` 里 `store.apply_remote_ops(&batch.ops)?` 的 `?` 让下一行 `set_sync_state(PULLED_KEY, ...)` **不执行**。于是游标停在原地，下一轮拉同一个 blob、走同一条路，永远出不去。而 push 段在 pull 段**之前**，所以上传不受影响——这正是它伪装成健康的原因。
- **解决**：未知表/坏 payload 的 op 进 `sync_quarantine` 隔离区（schema v11），游标照常前进；升级后 `migrate()` 重放。每条 op 包 `SAVEPOINT`，隔离前回滚防半写。详见 CHANGELOG 当日 Fixed。
- **避免**：**任何"逐条处理外部数据 + 处理完才推进游标"的循环，都要先回答"一条处理不了时会怎样"。** 三个答案里只有一个是对的：跳过（丢数据）、中断（卡死）、暂存后推进（正确）。这条不限于同步——导入、队列消费、批处理都同构。判据是：**单条坏数据的爆炸半径，绝不能大于那一条本身。**
- **顺带**：本仓已有先例做对过——`apply_one` 里孤儿 FK、重复内容都返回 `Ok(false)`（跳过，不报错），注释明确写着"that is data-dependent, not an error"。同一个函数里，**数据依赖的失败**走 `Ok(false)`、**认知边界的失败**走 `Err`，后者才是那条把整条链炸掉的。加新分支时想清楚自己属于哪一类。

## 2026-07-19 `hidden` 属性会被类选择器的 `display` 静默压过；DOM 断言别只查属性

- **现象**：为在桌面隐藏三个 Android 专属按钮，给容器加了 `hidden` 属性、JS 也按平台能力正确设了 `el.hidden = true`。代码、diff、`hasAttribute("hidden")` 断言三者全都"对"，但真浏览器里三个按钮照样 460×30 满尺寸渲染。
- **根因**：`hidden` 的隐藏效果来自 UA 样式表的 `[hidden] { display: none }`，属于**最低优先级**。容器同时带 `class="btnrow"`，而 `.btnrow { display: flex }` 是作者样式，直接压过 UA 规则。本仓库其实早就踩过一次——`.vhead .desc[hidden] { display: none; }` 就是当初为帮助浮窗单独补的点状补丁，这次没人想起来。
- **解决**：CSS 顶部加全局 `[hidden] { display: none !important; }` 一次兜死，删掉 `.vhead .desc[hidden]` 特例。前提是全站显隐都走 `el.hidden` 属性而非 `style.display`（已逐个核对 16 处，包括说明浮窗、隐藏文件输入、温度自定义输入）；若哪天有代码靠 `style.display` 覆盖 `hidden`，`!important` 会把它打死，届时要改用类名控制而不是撤掉这条。
- **避免**：**任何用 `hidden` 做显隐的元素，只要它带 class，就要确认那个 class 没设 `display`。** 更通用的一条：前端验证的 DOM 断言不能只查属性/类名这类"意图"，必须查渲染结果——`getComputedStyle(el).display`、`getBoundingClientRect()` 的宽高、`offsetParent === null`。这次正是靠 `computedDisplay: "flex"` 才抓出来的；只断言 `hidden === true` 会一路绿到上线。

- **避免**：任何可能超过几百毫秒的 command（网络、重 IO）一律 `async fn`；新增云端路径时想想「这条会不会在主线程上等网络」。

## 2026-07-17 Health Connect 分页、聚合与水位推进

- **现象**：直接调用一次 `readRecords` 会静默漏掉超过单页上限的数据；逐条累加 `StepsRecord.count` 会把不同来源或重叠区间的步数重复相加；即便本地 SQLite 写入失败，若仍推进 `health_since`，这段数据将永久漏采。
- **根因**：Health Connect 的读取 API 是分页接口，步数原始 record 不等于互斥采样，且拉取水位本质是「已可靠落库」承诺而不是「请求已发出」。
- **解决/避免**：对所有记录类型循环至 `pageToken == null`；步数用 `aggregate(StepsRecord.COUNT_TOTAL)` 的指定窗口总值；仅在转换和本地写入均成功后更新水位。新接入健康类型时，三条规则必须一并检查。

## 2026-07-16 Phase 6/7 实现中的两个边界坑（测试全绿 ≠ 边界正确）

1. **routine 整点触发被 `start <= now` 吃掉**
   - **现象**：165 个单元/集成测试全绿后做 CLI 真实走查，`pa fire --now 07:20`（routine 恰好设在 07:20）报「没有需要触发的提醒」。
   - **根因**：`materialize_routines` 用 `if start <= now { continue }` 跳过"今天已过点"的档位——`==` 也被跳过了。单测里物化时刻（10:00）与档位（07:20）总是错开，永远测不到相等的边界；而 CLI/ticker 恰好在整分钟运行，`==` 是常态而非罕见。
   - **解决**：改为 `start < now`（等于当下 → 物化 + 同一轮 `fire_due` 立即触发）；另注意水位（`scheduled_until`）一旦标过就不回填，修复后要用**全新库**复验，旧库里被跳过的那天不会补。
   - **避免**：涉及时间比较的代码，测试要显式覆盖 `==` 边界；改完边界后的验证不要复用带旧状态的库。
2. **`split_once(':')` 解析 `habit:07:20:护肤` 把时间劈成两半**
   - **现象**：`parse_habit_source` 单测直接失败，返回 `None`。
   - **根因**：机器可读的 source 格式里时间本身含冒号，`rest.split_once(':')` 在 `07` 后就切了。
   - **解决**：按固定宽度解析（`rest[..5]` 为 HH:MM，第 6 字节必须是 `:`，其余为标题）。
   - **避免**：自定义分隔格式时别让分隔符出现在字段内容里；出现了就固定宽度或换分隔符。

## 2026-07-16 `cargo fmt --check` 报全仓既有格式漂移，不能为新功能直接跑全量格式化

- **现象**：实现「今日聚焦简报」时按项目约定运行 `cargo fmt --check`，除本次新文件的少量换行外，还输出了 `pa-app`、`pa-alarm`、`pa-health-connect`、`pa-notif-access` 以及多个既有 `pa-core` 文件的大量 diff；其中包括工作树里用户正在进行的未提交改动。
- **根因**：当前工作树在本次功能开始前就不是 `rustfmt` 收敛状态，且存在跨多个 crate 的未提交格式差异。直接执行 `cargo fmt --all` 会扩大本任务范围并重写用户改动，无法把格式化改动与「今日简报」可靠区分。
- **解决**：只手动按 rustfmt 样式整理本次新增代码，保留原有工作树的格式状态；功能正确性继续由全工作区 `cargo test` 和 `cargo clippy --all-targets -- -D warnings` 验证。另一个独立的 Windows/MSVC 噪声是 `link.exe` 会把「正在创建库」这类正常进度写到 stdout，Rust 据此触发 `linker_messages` warning；`pa-app` crate 根仅对该 lint 加了 `#![allow(linker_messages)]`，避免它掩盖「全工作区零告警」结果（不影响真实 linker error）。
- **避免**：后续若要恢复格式门禁，应先由拥有既有改动上下文的人单独提交一次纯格式化变更，再把 `cargo fmt --check` 重新纳入 CI；功能任务不要用全仓 formatter 顺手改写脏工作树。

   - **根因**：Tauri Android 插件基类 `app.tauri.plugin.Plugin` 自带一个 `open fun requestPermissions(invoke: Invoke)`（服务于它自己那套 `@TauriPlugin(permissions=[...])` 声明式权限机制），Health Connect 的权限不是标准 Android 运行时权限，套不进那套机制，只能整个方法覆盖掉。

   - **避免**：写 Tauri 插件 command 时，方法名撞上 `Plugin` 基类已有方法（`checkPermissions`/`requestPermissions`/`registerListener`/`removeListener` 等）先去读 `~/.cargo/registry/.../tauri-x.y.z/mobile/android/src/main/java/app/tauri/plugin/Plugin.kt` 确认是否有同名 open 方法。
3. **`HeartRateRecord(...)` 构造函数在 1.1.0 要求显式 `metadata` 参数**
   - **现象**：`No value passed for parameter 'metadata'`，网上大多数 1.0.0-alpha 时代的示例代码没有这个参数。
   - **解决**：补 `metadata = Metadata.manualEntry()`（`androidx.health.connect.client.records.metadata.Metadata` 的伴生工厂方法，标记这条记录是本地手动/程序写入而非真实设备同步）。
   - **避免**：Health Connect 的 `connect-client` 库版本间数据类构造函数字段变动较快，遇到"缺参数"编译错时优先信编译器报的参数名，而不是照抄网上可能过时的示例。
4. **`adb`（在 Git-Bash/MSYS 环境）把 `/sdcard/...` 之类的绝对路径当成本地 Windows 路径转换**
   - **现象**：`adb pull /sdcard/screen.png <本地路径>` 报 `Error opening file: D:/git/Git/sdcard/screen.png`——设备上明明有这个文件。
   - **根因**：MSYS/Git-Bash 会自动把形似 Unix 绝对路径的命令行参数转换成 Windows 路径（当作本地路径处理），而 `adb` 的远端路径参数本不该被转换。

   - **避免**：这个 agent 的 Bash 工具是 Git-Bash（MSYS），凡是要把 Unix 风格路径原样传给非 MSYS 程序（`adb`、`scp` 到远端等）都先加这个环境变量，别在报错后才想起来。
- **旁证（验证方法论）**：这台开发用模拟器（Medium_Phone AVD，Android 17／API 37）把 Health Connect 做成了系统模块（`com.google.android.healthconnect.controller`），`HealthConnectClient.getSdkStatus()` 无需额外安装即返回 `SDK_AVAILABLE`；但设备上没有真实 Samsung Health 数据。验证 `readRecent()` 时临时给插件加了一个写权限 + `insertTestSample` command（写入一条合成 `HeartRateRecord`），跑通「写入→轮询→入库→UI 展示」全链路后再撤掉这段临时代码——Health Connect 不关心记录的来源 app，这是对读取路径的有效验证，不是走了捷径。

## 2026-07-12 `cargo tauri plugin new` 在非交互终端直接报错，退回手写脚手架
- **现象**：想用 `cargo tauri plugin new notif-access --android --no-api --no-example -a "..."` 生成通知权限跳转设置页的本地插件 crate，无论加不加 `--directory`、有没有用 `yes "" |` 喂空行，都报 `Error failed to prompt input: IO error: not a terminal`，直接退出。
- **根因**：该子命令内部用的交互式 prompt 库检测真实 TTY（isatty），管道 stdin 不算数；这个 agent 的 Bash 工具不是伪终端。
- **解决**：放弃脚手架命令，改为直接读已装好的参照插件源码（`~/.cargo/registry/.../tauri-plugin-notification-2.3.3`：`Cargo.toml`/`build.rs`/`src/{lib,mobile,desktop,error}.rs`/`android/{build.gradle.kts,src/...}`），照其结构手写最小插件（见 CHANGELOG「通知监听权限应用内引导」）。确认了一个关键机制：`cargo tauri android build` 靠 Cargo 依赖图里带 `links` 字段 + `tauri-plugin` build-dependency 的 crate 发现 Android 插件，把它们的 `android/` 路径**原地引用**进自动生成的 `gen/android/tauri.settings.gradle`（`project(':crate名').projectDir = new File("<crate的实际路径>/android")`）——本地 `path = "../xxx"` 依赖天然就能被发现，不需要发布到 crates.io，也不需要在插件自己的 `android/` 里放 `settings.gradle`（那是插件独立开发时自带示例 app 用的，会被自动生成的 glue 文件绕过）。
- **避免**：这个 agent 环境里凡是要真实 TTY 交互 prompt 的脚手架 CLI（`cargo tauri plugin new`、多数 `create-*` 工具）大概率会直接报错退出，别浪费时间在参数组合上试——直接找一个真实、结构相近的已装依赖包当参照手写，通常更快且更可控。

## 2026-07-06 Windows/MSVC 工具链：`link.exe` 与 `cl.exe` 不在 PATH 但仍可用
- **现象**：`which cl` / `which link` 在 Git-Bash 里，要么找不到 `cl`，要么把 `/usr/bin/link`（MSYS coreutils 的建链接工具）当成链接器——看起来像是缺 MSVC 工具链，会让人误以为得改用 `x86_64-pc-windows-gnu` 或装 MinGW。

## 2026-07-06 光凭「有时间词」就当事件，导致闲聊被误排日程
- **现象**：`route_intent("今天天气怎么样")` 被判为 `IngestEvent`；单元测试 `routes_chat` 失败。
- **根因**：路由用 `parse_datetime(...).is_some()` 当「有时间」，但解析器对「今天」这类纯日期词也会返回 Some（补默认 09:00），于是一句闲聊被当成待排事件。

- **避免**：解析「能不能解析出时间」和「值不值得当事件」是两件事，后者要更严格；解析器返回里保留 `explicit_time` 这类元信息供上层决策。

- **现象**：真机点击通知监听设置入口后，`adb` 短暂报告设备 `offline`，随后设备从列表消失；Solum 进程本身没有崩溃。
- **根因**：vivo 系统设置切换重置了 USB 调试传输，Windows 设备管理器随后也显示该手机 `Present=False`，不是 Activity 或 Rust 进程异常。
- **解决**：设备仍在线时可执行 `adb reconnect offline`，重连后再用 `dumpsys activity`、`pidof dev.solum.app` 和 `settings get secure enabled_notification_listeners` 分别确认前台、进程和权限状态；USB 设备已消失时只能重新插线并确认调试授权。
- **避免**：OEM 设置页跳转期间的 ADB 断连只能算传输层事件；重连并复查应用状态之前，不得把它记成应用崩溃。

## 2026-08-11 Tauri production CSP nonce 会拒绝现有内联 style 属性

- **现象**：arm64 debug APK 的页面能够加载、IPC 也正常执行，但 Android WebView 控制台连续报告 `style-src` 拒绝内联样式；初次 GPU 绘制较慢时，单张过早截图还会误判成白屏。
- **根因**：配置同时声明 `style-src 'unsafe-inline'`，Tauri production 构建又自动注入 nonce。按 CSP 规则，只要同一 directive 存在 nonce，浏览器就忽略 `'unsafe-inline'`，因此 HTML 中的 `style="..."` 属性被拒绝。
- **现状**：CDP 实测 DOM、计算样式、隐私门矩形和文本都存在，稳定帧能够正常显示；但被拒绝的显隐/尺寸属性仍是功能风险，且控制台噪声会掩盖真正错误。
- **避免**：优先把内联 style 迁入具名 CSS class，再保持严格 CSP；不要为了消日志直接开启 `dangerousDisableAssetCspModification`，除非单独完成安全评审并接受弱化 CSP 的代价。截图判白屏前先检查 DOM、控制台并等待稳定帧。
## 2026-08-12：PowerShell 5.1 的 UTF-8 脚本和本机 JSON 响应要显式声明编码

**现象**：独立监控应用脚本包含中文默认渠道名时，Windows PowerShell 5.1 会把无 BOM 的 UTF-8 脚本按系统代码页读取；本机 HTTP JSON 若只写 `application/json`，部分 PowerShell 客户端也会把 UTF-8 中文显示成乱码。

**根因**：PowerShell 5.1 对无 BOM UTF-8 的默认识别与 PowerShell 7 不同；HTTP 客户端的 JSON 编码推断也并不完全一致。

**处理**：`BenefitMonitor.ps1` 必须保存为 UTF-8 BOM；HTTP 响应统一带 `charset=utf-8`。验证不能只用浏览器，应同时做 PowerShell 5.1 语法/BOM 检查和 `Invoke-RestMethod` 中文 round-trip。

## 2026-08-12：本机监控的上游账号凭据不能放进公开配置

**现象**：用织境邮箱/密码替代手动 access token 后，若直接把密码或 refresh token 写进 `config.json`，浏览器读取 `/api/config` 时也会拿到长期凭据；只隐藏输入框并不能形成秘密边界。

**处理**：`config.json` 只保存邮箱和非秘密配置；密码、access token、refresh token 与到期时间整体用 Windows 当前用户 DPAPI 加密到 `secrets.dat`。`/api/config` 仅返回 `password_set/status/expires_at` 等脱敏状态。新账号保存采用先登录验证、失败回滚 secrets/state 的事务式流程，避免错误密码破坏现有会话。

**边界**：DPAPI 密文绑定当前 Windows 用户和系统环境，换用户或重装系统后通常需要重新登录。织境若启用 CAPTCHA 或 2FA，也必须扩展显式交互，不能把持续重试当作兼容方案。
## 2026-08-12 服务器按账号隔离了，客户端仍可能把 Alice 的库同步进 Bob

- **现象**：relay 的 SQL 已经处处带 `tenant_id`，Alice 的 token 也确实读不到 Bob 的 blob；但客户端运行中只有一份 `solum.sqlite`。如果只热切换登录令牌，数据库里 Alice 尚未上传的 oplog 会被 Bob 的 token 推进 Bob 租户，服务端隔离越正确，错误数据反而越稳定地留在 Bob 分区。
- **根因**：把“请求授权隔离”误当成了“数据归属隔离”。服务器只能判断当前令牌属于谁，无法判断客户端送来的密文原本是谁的本地库；用户名也不是稳定主键，改名或大小写规则变化都会换租户/路径。
- **解决**：账号由 solum-cloud 生成不可变 UUID；令牌 `sub`、relay 租户、本地 profile 与 Web Storage/IndexedDB 全部使用同一 UUID。登录先完成网络鉴权但不落盘，拿到旧 profile 的同步锁后才原子保存新会话并整进程重启，关闭所有旧连接和后台任务后再开另一 profile，不做只换 reasoner/token 的半热切换。进程自己注入的配置路径带 managed 标记，重启后跟随新 profile 重算；运维显式提供的环境变量不覆盖。桌面壳、CLI、Android 前台服务和通知监听器都必须复用同一 active-profile 规则，不能因为原生代码拿不到 Rust 环境变量就退回根目录。旧 guest 数据不自动认领给新账号。
- **避免**：任何“切账号”实现都列出进程内持久化与缓存清单逐项核对：数据库连接、后台队列/游标、配置文件、内存上下文、Web Storage、IndexedDB。判据不是“新账号的请求鉴权了吗”，而是“旧账号的任何字节还有没有路径被新账号的令牌发出去”。
